# 性能监测 Stats

「这场景卡不卡？」——在没装任何监测工具之前，这个问题的答案只能靠肉眼"感觉"。但人眼对帧率的感知非常粗糙：30FPS 和 45FPS 看起来都"有点不顺"，你根本分不清瓶颈是 CPU、GPU 还是内存。本节我们先把**性能可视化**做出来：在画布左上角挂一个 Stats 面板，实时显示 FPS / MS / MB 三组数据，再配合 Three.js 内置的 `renderer.info` 看 DrawCall 与三角形数。**只有看得见瓶颈，才能谈优化。**

## 一、为什么需要性能监测

3D 应用的性能问题通常分三类，它们的"症状"很相似但**根因完全不同**：

| 瓶颈类型 | 典型症状 | 根因 | 优化方向 |
|----------|----------|------|----------|
| **GPU 瓶颈** | FPS 低，但 CPU 占用不高 | 三角形太多、过度绘制、复杂着色器 | 减三角形、LOD、合并几何 |
| **CPU 瓶颈** | FPS 低，CPU 占用高 | DrawCall 太多、JS 计算过重 | InstancedMesh、合并几何、按需渲染 |
| **内存瓶颈** | 跑久了越来越卡，最终崩溃 | 资源未 dispose，GC 压力大 | dispose 全清理、复用对象 |

::: tip 肉眼判断的陷阱
"画面一卡一卡的"可能是上述任何一种。没有监测工具，你只能瞎猜——猜错的代价是花了半天优化 InstancedMesh，结果瓶颈其实在着色器。**先测量，再优化**是性能工作的铁律。
:::

## 二、Stats 面板是什么

`Stats` 是 Three.js 官方在 `examples/jsm/libs/stats.module.js` 提供的一个轻量性能监测小工具（其实就是 [stats.js](https://github.com/mrdoob/stats.js) 的 ES 模块版本）。它会在页面上添加一个不到 100×50 像素的小面板，实时显示三组数据之一：

| 模式 | 显示内容 | 单位 | 含义 |
|------|----------|------|------|
| 0 | FPS | 帧/秒 | 每秒渲染帧数，60 是流畅底线，30 以下肉眼可见卡顿 |
| 1 | MS | 毫秒 | 每帧渲染耗时，60FPS 对应 16.6ms，越低越好 |
| 2 | MB | 兆字节 | 已分配的 JS 堆内存，平稳=健康，持续上涨=泄漏 |

面板上还会画出最近一段时间的折线图，让你一眼看出"是稳定 60 还是跳来跳去"。

::: warning FPS 与 MS 的关系
FPS 是"每秒帧数"，MS 是"每帧耗时"。它们是倒数关系：`FPS = 1000 / MS`。那为什么还要两个模式？因为**当 FPS 接近 60 时，分辨率太低**——60FPS 对应 16.6ms，59FPS 对应 16.9ms，FPS 看起来几乎没变，但 MS 模式能清楚看到那 0.3ms 的波动。所以**调试瓶颈看 MS，看整体流畅度看 FPS**。
:::

## 三、导入 Stats 并挂到页面

Stats 不在 three 主包里，需要从 `examples/jsm/libs` 单独导入：

```js
import * as THREE from "three";
// 从 three 的 examples 子包导入 Stats 模块
import Stats from "three/examples/jsm/libs/stats.module.js";
```

导入后 `Stats` 是一个构造函数，调用 `new Stats()` 创建实例，再把它的 DOM 挂到页面上：

```js
let stats = null;

const initStats = () => {
  stats = new Stats();
  // showPanel(0) 选定显示模式：0=FPS, 1=MS, 2=MB
  stats.showPanel(0);
  // 把 Stats 的 DOM 节点挂到 body 上（它是一个绝对定位的小 canvas）
  stats.dom.style.position = "fixed";
  stats.dom.style.left = "12px";
  stats.dom.style.top = "12px";
  stats.dom.style.zIndex = "100";
  document.body.appendChild(stats.dom);
};
```

::: tip 为什么挂 document.body 而不是画布容器
Stats 的 DOM 是一个独立的 `<canvas>`，它跟你的 WebGL 画布没有父子关系。挂到 `body` 上是为了让它**永远在最上层**（配合 `zIndex`），不会被你的 UI 卡片或画布遮挡。如果你想让它跟着某个容器走，也可以 `container.appendChild(stats.dom)`，但记得容器要 `position: relative`。
:::

## 四、在渲染循环中调用 begin / end

光把面板挂上去还不够——Stats 需要"知道"每帧的开始和结束，才能计量耗时。所以必须在渲染循环的**开头**调 `stats.begin()`，**结尾**调 `stats.end()`：

```js
const animate = () => {
  animationId = requestAnimationFrame(animate);
  // 帧开始：Stats 开始计时
  if (stats) stats.begin();

  const dt = clock.getDelta();
  controls.update();
  // ... 各种动画更新
  renderer.render(scene, camera);

  // 帧结束：Stats 计算耗时并更新面板
  if (stats) stats.end();
};
```

::: warning begin / end 必须成对
如果你只调了 `begin` 没调 `end`，Stats 会一直累加时间，MS 数值会越来越大，FPS 越来越低——看起来像泄漏，其实是测量方式错了。务必成对调用，且 `render()` 要夹在中间。
:::

## 五、在 HouseScene.vue 中整合 Stats

把上面的步骤整合进 stage-13 的 `HouseScene.vue`，关键改动如下。先在全局变量区声明 `stats`：

```js
import Stats from "three/examples/jsm/libs/stats.module.js";

let stats = null; // Stats 性能面板
```

在 `initScene()` 末尾初始化 Stats：

```js
const initScene = () => {
  scene = new THREE.Scene();
  camera = new THREE.PerspectiveCamera(
    50,
    window.innerWidth / window.innerHeight,
    0.1,
    200
  );
  camera.position.set(12, 8, 12);
  camera.lookAt(0, 0, 0);

  renderer = new THREE.WebGLRenderer({
    canvas: canvasRef.value,
    antialias: true,
  });
  renderer.setSize(window.innerWidth, window.innerHeight);
  renderer.shadowMap.enabled = true;
  renderer.shadowMap.type = THREE.PCFSoftShadowMap;

  controls = new OrbitControls(camera, renderer.domElement);
  controls.enableDamping = true;
  controls.target.set(0, 1.5, 0);
  controls.update();

  clock = new THREE.Clock();

  // ★ 初始化 Stats 性能面板
  stats = new Stats();
  stats.showPanel(0); // 0=FPS, 1=MS, 2=MB
  stats.dom.style.position = "fixed";
  stats.dom.style.left = "12px";
  stats.dom.style.top = "12px";
  stats.dom.style.zIndex = "100";
  document.body.appendChild(stats.dom);
};
```

在 `animate()` 里夹 begin / end：

```js
const animate = () => {
  animationId = requestAnimationFrame(animate);
  if (stats) stats.begin(); // ★ 帧开始

  const dt = clock.getDelta();
  controls.update();
  updateDoor(dt);
  updateLamp(dt);
  updateDayNight(dt);
  updateSmoke(dt);
  updateLeaves(clock.elapsedTime);
  renderer.render(scene, camera);
  updateRenderInfo();

  if (stats) stats.end(); // ★ 帧结束
};
```

最后在 `disposeScene()` 里移除 Stats DOM：

```js
const disposeScene = () => {
  if (animationId) cancelAnimationFrame(animationId);
  // ... 其他清理

  // ★ 移除 Stats 面板 DOM，避免 SPA 切换后残留
  if (stats) {
    if (stats.dom && stats.dom.parentNode) {
      stats.dom.parentNode.removeChild(stats.dom);
    }
    stats = null;
  }

  // ... 后续 geometry / material / renderer 清理
};
```

::: warning 别忘了移除 DOM
Vue 是 SPA，组件卸载时如果你只把 `stats = null` 但没移除 DOM，那个小面板会**残留在页面上**直到刷新。所以 `removeChild` 必不可少——这是性能优化教程里最容易忽略的"清理细节"。
:::

## 六、切换 Stats 显示模式

Stats 默认显示 FPS（panel 0）。你可以用 `showPanel(n)` 程序化切换：

```js
const setStatsMode = (mode) => {
  // mode: 0=FPS, 1=MS, 2=MB
  if (stats) stats.showPanel(mode);
};
```

在 stage-13 里我们绑了一个 `S` 键来循环切换。用一个模块级变量 `statsMode` 记录当前模式，按一次 S 就 `(statsMode + 1) % 3`：

```js
let statsMode = 0; // 0=FPS, 1=MS, 2=MB

const onKeyDown = (e) => {
  const key = e.key.toLowerCase();
  if (key === "s") {
    // 循环切换 0 → 1 → 2 → 0
    if (stats) {
      statsMode = (statsMode + 1) % 3;
      setStatsMode(statsMode);
    }
  }
};
```

::: tip 也可以点击切换
Stats 面板本身是可点击的——直接用鼠标点一下那个小面板，它就会循环切换 FPS → MS → MB → FPS。所以 S 键只是个"程序化"的便捷方式，本质上和点击一样。
:::

## 七、读懂 FPS / MS / MB

把面板装上后，怎么"读"它？这里给一个速查表，帮你在不同数据下判断瓶颈类型。

### 7.1 FPS 模式（panel 0）

| FPS 范围 | 体感 | 判断 |
|----------|------|------|
| 55~60 | 流畅 | 健康，无需优化 |
| 30~55 | 略卡 | 有瓶颈，看 MS 模式找根因 |
| <30 | 明显卡 | 严重瓶颈，优先排查 DrawCall 和三角形数 |
| 跳来跳去（30↔60） | 周期性卡顿 | 多半是 GC（垃圾回收）触发，看 MB 模式 |

### 7.2 MS 模式（panel 1）

| MS 范围 | 对应 FPS | 判断 |
|---------|----------|------|
| <16.6ms | 60+ | 健康 |
| 16.6~33ms | 30~60 | 有压力 |
| >33ms | <30 | 卡顿 |

如果 MS 折线**周期性出现尖峰**（平时 10ms，偶尔飙到 50ms），多半是 GC 在回收内存——这时切到 MB 模式看堆内存曲线是不是"锯齿状"上升。

### 7.3 MB 模式（panel 2）

| 曲线形态 | 判断 |
|----------|------|
| 平稳（一条水平线） | 健康 |
| 锯齿状（上升→骤降→上升） | GC 周期性触发，通常可接受 |
| 持续单调上升不回落 | **内存泄漏！** 必须排查 dispose |

::: warning MB 模式只反映 JS 堆
注意 Stats 的 MB 数据来自 `performance.memory`（仅 Chrome 支持），它反映的是 **JS 堆内存**，不包括 WebGL 显存。你的 geometry/texture 占用的 GPU 显存不在这个数字里。要查显存得用 Spector.js 或 Chrome 的 WebGL Inspector。即便如此，MB 模式仍是排查"JS 端泄漏"的第一工具。
:::

## 八、配合 renderer.info 看 DrawCall

Stats 面板告诉你"卡不卡"，但不告诉你"为什么卡"。Three.js 还内置了一个 `renderer.info` 对象，记录了**上一帧**的渲染统计：

```js
renderer.info.render.calls;     // DrawCall 次数（每多一个 Mesh/Points 就 +1）
renderer.info.render.triangles; // 渲染的三角形总数
renderer.info.render.points;    // 渲染的点数（粒子）
renderer.info.render.lines;     // 渲染的线段数

renderer.info.memory.geometries; // 当前已上传 GPU 的几何体数
renderer.info.memory.textures;    // 当前已上传 GPU 的纹理数
renderer.info.programs;           // 当前编译的着色器程序数
```

在 stage-13 里，我们把 `calls` 和 `triangles` 实时读到 UI 卡片上：

```js
const updateRenderInfo = () => {
  if (!renderer) return;
  ui.drawCalls = renderer.info.render.calls;
  ui.triangles = renderer.info.render.triangles;
};
```

::: tip DrawCall 是什么
"DrawCall"是 GPU 渲染管线的**一次绘制调用**。每调用一次 `renderer.render()`，Three.js 会遍历场景图，对每个可见的 Mesh/Points/Line 发起一次 DrawCall。DrawCall 越多，CPU 给 GPU"发指令"的开销越大——**1000 个独立 Mesh 渲染 1000 个三角形，远比 1 个 Mesh 渲染 1000 个三角形慢**。降低 DrawCall 是性能优化的核心目标之一。
:::

## 九、本阶段优化对照表

把 Stats 和 renderer.info 都装好后，本阶段的"优化成果"可以量化对照：

| 优化项 | 优化前 | 优化后 | 看哪个指标 |
|--------|--------|--------|-----------|
| 落叶（200 片） | 200 个 Mesh = 200 DrawCall | 1 个 InstancedMesh = 1 DrawCall | `render.calls` 降 199 |
| 碎石小径（30 块） | 30 个 Mesh = 30 DrawCall | 1 个合并 Mesh = 1 DrawCall | `render.calls` 降 29 |
| 远处家具（4 件） | 高精度版 ~50 三角形/件 | 低精度版 12 三角形/件 | `render.triangles` 明显下降 |
| 静态按需渲染 | 每帧都渲染（~60FPS） | 不动时不渲染（~0% GPU） | Stats MS 模式几乎为 0 |

按 P 键切到"静态按需渲染"模式后，Stats 的 MS 数值会从 ~5ms 瞬间降到 ~0.2ms——这就是"按需渲染"的威力，下一节会详细讲。

## 十、常见误区与排查清单

初学者用 Stats 时常踩的坑，对照排查：

- **Stats 面板不显示**：检查 `document.body.appendChild(stats.dom)` 是否执行；检查 `zIndex` 是否被其他元素盖住
- **Stats 数值一直是 0**：检查 `begin()` / `end()` 是否成对调用，且 `render()` 夹在中间
- **Stats 数值越来越大**：`begin()` 调了多次但 `end()` 只调一次，或者反过来
- **MB 模式显示 0**：非 Chrome 浏览器（Firefox/Safari 没有 `performance.memory`），换成 Chrome 即可
- **DrawCall 数比预期多**：检查是不是有 `frustumCulled = false` 的物体（粒子系统常关掉），它们即使不在视锥内也会被渲染

::: tip 性能优化的工作流
本节建立的"工作流"是：**先看 FPS 判断是否卡顿 → 切 MS 看每帧耗时 → 看 renderer.info 找瓶颈源头（DrawCall 还是三角形）→ 针对性优化 → 再看 FPS 验证效果**。这个循环是所有性能工作的标准流程，本章节后续两节都会基于这个流程展开。
:::

## 本节总结

| 知识点 | 关键 API | 说明 |
|--------|---------|------|
| Stats 导入 | `import Stats from "three/examples/jsm/libs/stats.module.js"` | Three.js 官方性能监测小工具 |
| 三种模式 | `showPanel(0/1/2)` | FPS / MS / MB，点击面板也可切换 |
| 帧计量 | `stats.begin()` / `stats.end()` | 必须成对，且夹住 `render()` |
| DOM 挂载 | `document.body.appendChild(stats.dom)` | 用 fixed + zIndex 保证在最上层 |
| 渲染统计 | `renderer.info.render.calls / triangles` | 看瓶颈是 DrawCall 还是三角形数 |
| 资源统计 | `renderer.info.memory.geometries / textures` | 看资源是否泄漏（持续上涨=泄漏） |
| 性能工作流 | FPS → MS → info → 优化 → 验证 | 先测量再优化，避免瞎猜 |
